# Working on the AnIdeaLab brain kit

This repo is the brain kit: the brain a new owner starts with, the installers that set it up on their PC or Mac, and the brain updates that brains made from it get. You're working on the kit, not in a brain. What each folder is: [README.md](README.md#whats-here).

**brain/CLAUDE.md is not for you.** It's the core a new owner's agents read, so if it shows up in your context, it's the file you're editing, and its instructions (getting started, guide mode, the owner's defaults) are for their brain. `{KIT_DATE}` and `{KIT_ISO}` in brain/ stand where each brain gets its own start date: leave them as they are.

**The kit stands alone.** Nothing in it names or depends on any one person, their brain or their accounts: it's AnIdeaLab's. A rule's reason is given in the kit's own words. What owners' brains report back, and what AnIdeaLab learns from its own use, comes in as a change made here, never as a copy of someone's files.

## Changing the kit
1. **Change the files here directly.** brain/ is the source: nothing else writes it.
2. **Run `python3 tools/kit.py build`** after every change. It rebuilds brain/'s indexes, copies [sign-off-links.md](sign-off-links.md) into brain/, makes a new brain from brain/ in a scratch folder, and runs that brain's own checks and tests, and the kit's promises: no one person's names, accounts or setup anywhere in the repo (the copied skills aside, kept as they came), every date placeholder filled, the core under 6 KB (a core may be 8 KB, so each owner has 2 KB for their own lines), and as many skills as START-HERE.txt says. Then it makes a brain the way the Mac installer does (`install/install-mac.sh` in its check mode) and checks that too; it stops if a line of brain/ that the Mac installer says for a Mac has changed, so change that line's Mac version in install-mac.sh's `mac_brain` to match, and keep the Mac core under 6 KB too. Fix what it reports before you commit. GitHub's own Macs try the whole Mac installer on each push that touches it or brain/ ([mac-installer.yml](.github/workflows/mac-installer.yml)).
3. **Copied skills** are kept as they came, and brought up to date from their own sources: from brain/, run `python3 skills/brain-spec/skill_updates.py check`, then `update --source <owner/repo>` for a set that changed, read the diff, and run the build. Where each came from: [brain/skills/lists/sources.md](brain/skills/lists/sources.md).
4. **Commit** in small commits with plain messages: brain/ on the `next` branch, everything else on `main` (below), with `git pull --rebase origin <branch>` before you start and before you push. Never force-push.

## How a change reaches owners
A new brain is made from brain/ as it is on `main`, and marked with the newest update in updates/. On a Mac, since brain/ is made for a Windows PC, install-mac.sh also adds install/mac-brain/'s files (the Mac runner's workflow, skill and note) where brain/ doesn't have them, and says a few of brain/'s lines for a Mac (its `mac_brain` lists them). When an update brings those files into brain/, delete them from install/mac-brain/: the build says when brain/ has them. A brain already made gets a change only through a brain update, which its owner says go to, and `brain_update.py apply` merges it in from brain/ as it was in the commit that sent the update before, which is also what `compare` holds a brain to.

So **brain/ on `main` changes only in an update's commit.** Work on brain/ goes on the `next` branch (make it from `main` if it isn't there): commit and push there, run the build there, and merge `main` into it whenever `main` moves. The rest of the repo (install.ps1, install.sh, install/, inbox/, testing/, tools/, .github/, sign-off-links.md) changes on `main` as usual, since none of it is in a brain; the build's copy of sign-off-links.md into brain/ is the one brain/ change between updates, as brains refresh theirs from the root copy each day anyway.

## Sending an update
1. **The message** goes in updates/ as `NNNN-<a-few-words>.md`, with its line in [updates/README.md](updates/README.md), in the shape of the last one: "Brain update N from AnIdeaLab: <words>", "Sent <date>.", an opening paragraph, "Summary for the owner" (a few plain lines, and what touches their PC), "What changed, and why", "The setup this brain should have afterwards" and "What to do beyond the files". The owner's agent reads it cold, in a brain that may have drifted, so give each change its reason and each step what to do if the brain differs. An update changes files only: anything that must run on the owner's PC is a command for them to paste. Where a step depends on a check the agent may only half be able to run (a GitHub call a session's proxy refuses), say what to do then.
2. **The clashes to expect** get a step each whenever the update touches their file: the core's first line and its defaults' opening line, where owners add their own; the owner's routines and time zone in routines.md; the owner's folders in knowledge/systems/my-pc.md; on a brain set up on a Mac, the lines the Mac installer said for a Mac (the core's two defaults about the owner's computer, the front door's, the PC's note and the starting rules) and its Mac parts; a brain's own history in knowledge/areas/the-brain/README.md; the shelves' indexes (`library.py build` writes them again); and a core over 8 KB once the owner's lines are back (their rule's detail moves into a decision note, never cut).
3. **Trying it** on a stand-in brain at the update before, in a clone of this repo that can't push (`BRAIN_KIT_URL=file://<clone>`, its own `XDG_CACHE_HOME`), takes a few minutes; trying it on copies of owners' brains, by an agent acting as each brain's own, takes most of a session. Say which before starting, so whoever is sending it can choose to send it untried: the message's steps are what owners' agents go by either way.
4. **Send it:** the message as the last commit on `next`, then `git checkout main && git merge --ff-only next` and push. In the next commit, link the exemplar at the message's end: `https://github.com/AnIdeaLab/brain-kit/tree/<the update's commit>/brain`. A brain on the update before should then list it with `brain_update.py check`. A fix to a message's wording reaches every brain that hasn't applied it, since brains read messages from the newest `main`.

Brains made before update 5 came from the kit's earlier home; update 5 pointed them here, and brought them to the kit as it stood that day.

# The weekly tidy-up
Once a week, the agent cleans the brain up and gives the owner a short report, so the brain stays tidy and true as it grows. It's light on purpose, and a reminder, not a scheduled job: `reminders.py` says when it's due, the agent tells the owner, and it runs only if they say yes. What past ones found is in [the audit log](../../knowledge/areas/the-brain/audit-log.md).

**Two levels.** This weekly one is cheap. Once a month, [the deep audit](deep-audit.md) reads that month's new decisions in full against the rest, to catch what only reading does.

**Keep it light.** It uses the owner's plan. Read cards, not notes: the shelves' indexes and `library.py find` show every card; open a note only when a card or a script points at a problem. For "what happened this week", read commit messages, not the notes themselves.

## A busy project gets its own agent
Most weeks the agent does the whole tidy-up alone, as below. But a project that moved a lot fills the agent's memory with one subject's detail, and the rest of the brain gets a tired read. So after step 2 of the clean-up, count what moved for each project and area since the last tidy-up: its notes changed (`git log --since="<the last tidy-up's date>" --name-only --format= -- knowledge/ventures/<name>`), its tasks, and its hand-offs waiting to be folded in (`library.py find --tag <name> --shelf handoffs --all`).

| The week | The method |
|---|---|
| **Quiet:** no project with more than about ten notes, tasks and hand-offs moved | The agent alone. No other agents |
| **One busy project** | One agent for that project; the agent does the rest |
| **Two or more busy projects** | An agent each, one or two at a time, then a links agent |

It uses more of the owner's plan than a quiet week's tidy-up, so say which projects are getting an agent, and why, before starting them. More than two at once needs the owner's yes.

- **A project's agent** gets a brief ([handoff](../handoff/SKILL.md#briefs-and-reports)) for that project alone, and does this skill's steps for it in place of the coordinator: steps 3 to 7 and 13 of the clean-up for the project's own notes, tasks and hand-offs, the links between its own notes, and its "Where it stands" (Part 4, step 1). It edits only notes in the project's folder or tagged with its name, commits only those paths, and reports back: what it changed, what it folded in from which hand-offs, what crosses into other projects (a person, a date, money, a dependency), and what to ask the owner ("keep or drop?" among them).
- **The links agent** reads those reports, and the "Where it stands" of the projects that had no agent. It reports what crosses between projects and where each link belongs, line by line, and edits nothing ([file-intake](../file-intake/SKILL.md#the-links-agents-brief) has its brief's shape).
- **The coordinator,** the agent the owner said yes to, checks each report once, writes what crosses projects from the links agent's list, and does everything that belongs to the whole brain: the scripts, updates, decisions, the quiet projects, the friction log, the skills' lessons and the report. Only it writes across projects, so agents side by side don't clash.

## 1. Clean up
1. **Brain updates first.** Pull, and if the session can reach github.com, run `python3 skills/brain-spec/brain_update.py check`. If any are waiting, read the owner their summary first, even if they asked for the update by name, and apply them, all together, only once they say go ([brain updates](../brain-spec/SKILL.md#brain-updates)).
2. Run `python3 skills/brain-spec/library.py check`, `python3 skills/brain-spec/check_links.py` and `python3 skills/brain-spec/library.py audit --since <the last tidy-up's date>`. Fix what they report. In a shallow clone (a cloud session's, often) the audit counts what the clone's history holds and says what it couldn't see; `git fetch --unshallow origin main` first gives the whole picture.
3. Reread the notes the audit lists as changed a lot since their card's `updated` date; fix any card that no longer matches, and set `updated` to today.
4. Two cards that say nearly the same thing: merge the notes, and mark the merged-away one `dropped` or `superseded` with a link to the one that stays. Split a note doing two jobs.
5. For each task finished since the last tidy-up, save anything learned that never became a note ([brain spec](../brain-spec/SKILL.md#saving-knowledge)).
6. **Stale tasks.** The tasks shelf should hold only what's still to do. A task closes only when the agent working on it closes it, so unfinished ones pile up, many unchanged for weeks.
   - List every open, doing or waiting task whose note hasn't changed in two weeks (`git log -1 --format=%cs -- <task>`), and open each. Check the commits and the notes it names to see where it really stands.
   - Close what's finished or overtaken: mark it `done` (saving what was learned, as in step 5) or `dropped`, with a dated line under `## Progress` saying why. Merge two tasks that are the same job. Never mark the owner's part done on a guess: a task they hold that you can't settle goes to them as "keep or drop?".
   - Move every `done` or `dropped` task that hasn't changed in two weeks to `knowledge/tasks/history/` with `python3 skills/brain-spec/move.py`, then reword any live note's link to it into words, as the brain spec says for history; make the folder's `README.md` if it isn't there yet.
7. **Hand-offs.** They pile up too, and what's lasting in them belongs in the brain's notes, so the tidy-up folds them in and cuts them down. Read the [hand-offs shelf's](../../knowledge/handoffs/README.md) index, the board, and list the done ones not yet in `history/` with `python3 skills/brain-spec/library.py find --shelf handoffs --status done`. For each done one, save what's lasting in it that never became a note (decisions, facts, lessons and tasks, by the brain spec's test), then move it unchanged to `knowledge/handoffs/history/` with `move.py`, kept as the raw record, and reword any live link to it into words; make the folder's `README.md` if it isn't there yet. No new session hand-offs are written (a job's task note is its status), so for an old `session` one still open, check its job's task note says where it stands, moving in anything it lacks, and mark the hand-off `done`. An open or picked-up one that hasn't changed in a week: check the commits for where its work stands, mark it `done` with a dated line if the job is finished or a newer hand-off carries it on, and cut down one that has grown past what's still true (git keeps the original).
8. A decision a newer one contradicts gets `status: superseded` (or `partly-superseded`, saying which part stands) and a link to the newer one, and the old rule mustn't survive in the core or other notes. The audit's lists of clashing decisions and notes citing a superseded one (step 13) point at most of them.
9. Ideas and parked projects nobody has touched for months go to the owner as "keep or drop?".
10. Every folder in `skills/` has a line in a list by topic (`library.py check` names any that hasn't), no line names a skill that's gone, and every copied skill has its line under its source in [lists/sources.md](../lists/sources.md), the record the scripts read to tell copied from the brain's own. If the session can reach github.com, run `python3 skills/brain-spec/skill_updates.py check` and bring changed sets up to date ([find-skills](../find-skills/SKILL.md#keeping-them-up-to-date)).
11. **Keys.** Read the newest run in [the keys check log](../../knowledge/systems/keys-check-log.md), which the Check keys workflow writes each week; if its date is more than a week old, start `.github/workflows/check-keys.yml` (or ask the owner to, from the repo's Actions tab) and read it after. Give a row in the keys table ([keys and accounts](../../knowledge/systems/keys-and-accounts.md#keys)) to any secret listed without one, and a check line in [key-checks.json](../add-a-key/key-checks.json) to any marked "no check yet". A key that's refused goes in the report as something for the owner, with the one command to add it again ([add-a-key](../add-a-key/SKILL.md)).
12. **Devices.** If any computer has a runner, run `python3 skills/brain-spec/devices.py status` (or start "Which devices are on" with the label empty) and bring [devices](../../knowledge/systems/devices.md) up to date: a computer renamed, retired or new, a way in that changed, a disk nearly full. One that's off is fine; say so in the report.
13. **What slipped through.** The audit's last lists name what was saved in the wrong place, against the brain spec's ["Saving knowledge"](../brain-spec/SKILL.md#saving-knowledge), whose examples say what goes wrong if it stays. The script only finds; open each thing it names and judge. It's where the tidy-up's attention is set: when a new kind of slip turns up (the owner corrects one, or you find the same mistake in a few notes), add a list for it to `slipped()` in [library.py](../brain-spec/library.py), with a line in its test, and a line here saying what to do with it. Biggest first; what you can't finish this week goes in the report, and a task another chat is holding (its note changed in the last two days) gets only a Progress line saying what to fix.
    - **Status swollen or stacked:** rewrite the task's status parts to what's true now, keeping each fact that's still true. Research, findings and numbers in it go to a note on the project's shelf, linked in a line. Progress past 10 lines: first put what's still true in the old lines into the status, Watch-outs or Decisions, then move all but the last 5 word for word to the project's `history/` (`<task>-progress.md`), with a line at the top of Progress saying where. A project note's "Where it stands" past a screen is rewritten as a few lines linking its tasks.
    - **The owner's answers left in tasks:** each goes as a dated line, in their words, in the project's `decisions/<project>/answers.md` (or a note of its own for a big choice), and the task's line becomes a link to it. The agent's own calls stay.
    - **Watch-outs in tasks finished since then:** one about how to do a kind of job goes in that skill's `LESSONS.md`, to be folded in at Part 3; one about that job alone stays.
    - **Current decisions that say they replace another:** read both, and mark the older one `superseded` or `partly-superseded` with a link, then search for its file name and the old rule's words and fix what still gives it. A pair where one only mentions the other goes in `skills/brain-spec/checked_links.txt`, so it isn't listed again. **Notes citing a superseded decision:** point them at the one that replaced it, or reword.
    - **Graduated ideas still a full plan:** move what's still useful into the project's notes and cut the idea to a few lines and a link.
    - **Notes whose date has passed:** update the note, or close the task; one the owner holds goes to them as "keep or drop?".
    - **Decision notes past 10 KB:** a decision that big is carrying the work's log (takes, rounds of notes, findings), which every deep audit then reads. Keep the decision, its reasons and every word of the owner's; move the agents' working notes to a note on the project's shelf, word for word, and link it in a line.
    - **Logs and `answers.md` past 10 KB:** move entries older than two months (in `answers.md`, the replaced lines) to the shelf's `history/`, and say where at the top.
    - **Code and big or media files in `knowledge/`:** a project's code belongs in its own repo ([how](../brain-spec/SKILL.md#a-project-with-code-gets-its-own-repo)); media on the PC. Moving a project out is a job of its own, so put it in the report as a suggestion, with what would move where. A file the owner gave the brain that became a note stays next to it, as its raw original.
    - **Stray files** (`Untitled` files from Obsidian, anything at the top level that isn't one of the brain's parts): delete the empty ones; move the rest into a shelf, or ask.
    - **Branches already merged into main:** delete them (`git push origin --delete <branch> ...`). The list leaves out any touched in the last two days, whose session may still be going.

## 2. The friction log
For each open row in the [friction log](../../knowledge/ideas/friction-log.md) added since the last tidy-up: would know-how that stays the same from job to job have saved the trouble? If yes, find or write a skill for it ([find-skills](../find-skills/SKILL.md)), and move the row to "Solved" naming the skill. If it needs the owner (an account, a key, a payment), a tool nobody has built, or something outside the brain's control, it stays open.

## 3. Skill lessons
`library.py audit` lists every skill with a `LESSONS.md`. Fold each skill's lessons in, the brain's own, the kit's own and copied ones alike: put each lesson into the step it belongs to by rewording that step, delete it from `LESSONS.md`, and delete the file and its link once it's empty; at most 4 changes to one skill a week. Folded in, a lesson changes how the skill is done, rather than sitting in a list beside it that agents may not read. A brain update merges its changes around the folded lines, and where both changed the same place, the brain spec's "Brain updates" says to put the owner's lesson back.

## 4. The report
1. **Where each project and area stands:** a summary of the week and where everything is, as short as it can be without losing the detail that's needed. For each project in `knowledge/ventures/`, and each area in `knowledge/areas/` (the brain itself, and any the owner adds), whose notes, tasks or code changed since the last tidy-up, rewrite the "Where it stands" part of its note (one that has none gets one, under its opening lines) from the week's commits (`git log --since="<the last tidy-up's date>" --format="%ad %s" --date=short`) and its tasks (`python3 skills/brain-spec/library.py find --tag <name> --shelf tasks`). Rewrite it, don't add to it: date it with today, and say what's true now (what's built or live, what's being worked on, what waits on the owner or anyone else, the numbers that matter). Drop what's only history, since the commits and the notes keep it, and keep every fact still true. Keep it short, each line linking the note or task that holds the detail, so it's a map over the notes, not a second copy that drifts. A project or area that didn't move keeps its paragraph and its date.
2. Add an entry at the top of [the audit log](../../knowledge/areas/the-brain/audit-log.md), with a heading starting with today's UTC date, like `## 24 Oct 2026: tidy-up`: what was fixed, what waits on the owner, and two or three suggestions marked as the agent's own. That heading is what turns the reminder off until next week.
3. Commit in small commits with plain messages, and push.
4. Tell the owner the short version in the thread: what changed, what waits on them, and the suggestions. End with one line: guide mode is at level <N> of 4 (the core's line), and they can move it down for more explaining or up for less ([the levels](../guide-mode/SKILL.md#the-owners-level)).

## Don't
- Don't rewrite a project's plans, or decide for it: Part 4's first step rewrites only where it stands.
- Don't change links just to make the map look tidier; agents use them to find their way.
- Don't touch the brain graph's code (`.obsidian/plugins/brain-graph/`) unless the owner asks.

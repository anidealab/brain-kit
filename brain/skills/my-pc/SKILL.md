# Running jobs on the owner's PC
The owner's PC is a GitHub Actions self-hosted runner for this brain's repo, with the label `my-pc` (and `gpu` if it has an NVIDIA card). It runs under the owner's own account, without admin rights, so a job can reach their files and apps. It starts by itself, hidden, when they sign in to Windows, so the PC has to be on, awake and signed in (a locked screen is fine; after a restart, nothing runs until they sign in). A PC set up by an earlier kit runs it as a Windows service with their password instead, which starts with Windows and has admin rights; it still works, and `setup-runner.ps1` again moves it over. What this PC has is in [the PC's note](../../knowledge/systems/my-pc.md).

## Not set up yet
If [devices](../../knowledge/systems/devices.md) has no computer of the owner's (a brain made from the template starts with only cloud sessions), the runner may not be set up. **Check quickly, then answer:** look at the tasks shelf for a setup task and at `git log` for an installer's commit ("Added the Mac parts", "runner is set up", "Setup report for AnIdeaLab"), and run `python3 skills/brain-spec/devices.py status`, which says at once when nothing points to a computer. If none of these does, it isn't set up: tell them straight away, with no further wait. Only when something points to one does `status` ping `my-pc` and `my-mac`, which can take a minute: say you're checking before it starts. A computer whose install ran after the last session ended answers there though nothing in the brain lists it: test it and add its row ([getting-started, step 4](../getting-started/SKILL.md#4-the-owners-computer)), then do the job. If they say they've run the command and nothing points to it yet, `status --ping` checks anyway. The Claude app's own list of computers is a different way in, so an empty one says nothing about the runner. Only if none of these finds one is the runner not set up. When they ask for something that needs their computer (their files, an app on it, a GPU, anything a cloud session can't do), don't send them to a local session or give click-by-click steps. Say it needs their computer added to the brain first, and make it sound as easy as it is: one command to paste and a few yes or no questions, then it sets itself up while they get on with something else, and it's only ever done once. Don't give a time. If they'd like it, do [getting-started's step 4](../getting-started/SKILL.md#4-the-owners-computer), which has the command for each computer, then the job. If not, do what you can from the cloud and save the rest as a task they hold.

## Running a command
Start the workflow [`pc-run.yml`](../../.github/workflows/pc-run.yml) ("Run on my PC") on `main` with the GitHub tool's run-workflow method. Inputs:
- `command`: the command or a whole script. Start it with a `# comment` saying what it's for: the run's name in the Actions list starts with it.
- `shell`: `powershell` (Windows PowerShell 5.1, the default), `cmd` or `bash` (Git Bash).
- `workdir`: where it runs. Default `C:\AI-Brain-Link`.
- `timeout`: minutes, default 60, up to 4320 (three days).
- `checkout`: true to get this repo at `$env:GITHUB_WORKSPACE` first, so the command can run the repo's scripts. Set it whenever the command calls them: without it, the job quietly runs whatever older copy the last checked-out job left in `_runner\_work`, with no error.
- `artifact`: a file, folder or wildcard on the PC to attach to the run for 3 days, so you can look at it (stills, a small file). The GitHub tool's artifact download gives a short-lived link.

Then find your run in the workflow's run list, wait until it shows as completed, and read the job log. A copy of each run's output stays on the PC in `C:\AI-Brain-Link\_logs\pc-run-<run id>.log`.

From a cloud session, the `gh` command line usually works through the session's proxy even when `gh auth status` calls the token invalid, so try the command itself (`gh run view <id> --json status,conclusion`, `gh run view <id> --log`); a loop on `gh run view` in a background shell says when a job ends. If `gh` is refused, the GitHub tool's actions methods do the same: list the run's jobs for the job's id, then read that job's log.

**How the queue and logs behave:**
- Jobs run one at a time, in order. Don't add a concurrency group to the workflow: GitHub keeps only one waiting run per group and cancels the others.
- A job's log can only be read once it has finished (asking earlier gets a 404). **To follow a long job as it runs,** read the issue "PC job live log" in this repo (the GitHub tool's issue read): the workflow writes the log's last 80 lines there every 30 seconds, and once more at the end, with the run's link at the top. It's made on the first job, and skipped if the repo is public. Check the run list for "completed" to know it's done.
- If the run-workflow call times out, the run may still have been queued. Check the run list before trying again.
- Jobs check out `main` when they start, so push a script before starting the job that runs it.

## Getting files to and from the PC
- **From the PC:** the `artifact` input.
- **To the PC,** for a file the owner gave a cloud session: push it alone to a temporary branch (`git hash-object -w`, `git mktree`, `git commit-tree`, then push to `refs/heads/transfer/<name>`), fetch it in the job with `git fetch --depth 1 origin transfer/<name>` and `git archive -o "$env:RUNNER_TEMP\x.zip" FETCH_HEAD`, then `Expand-Archive`. Then delete the branch with the workflow [`delete-branch.yml`](../../.github/workflows/delete-branch.yml) ("Delete branches", input `branches`), since a session's git proxy refuses branch deletes. It keeps `main` clean.
- **Other leftover branches,** like a session's own `claude/...` branch once its work is on `main`, go the same way: the workflow takes several names at once, never deletes `main`, and logs each branch's last commit so it can be pushed back (an owner's brain, 22 Oct 2026).

## Things to know
- **No pop-ups, no admin rights.** Nobody is there to click. Use installers' silent switches (`winget install --silent`, `/S`, `/quiet`), and a per-user install where there is one (`winget install --scope user`). Jobs run without admin rights, so anything that needs them (a machine-wide installer, the PC's own PATH, Program Files) asks on the owner's screen and waits there until the timeout: give the owner a command to paste instead, and say it will ask for admin rights.
- **Windows a job opens show on the owner's screen,** since the runner runs in their signed-in session. Start programs hidden or minimised where they have a switch for it, and close what the job opened.
- **Files the older service made belong to Administrators,** because it ran with the owner's full admin rights. The owner's own git (Obsidian's Git plugin, for one) then refuses a repo it made or copied ("dubious ownership"). Fix it with a command for the owner to paste into PowerShell as administrator: `icacls <folder> /setowner "<what whoami prints>" /T /C`. A runner set up at sign-in makes files that are the owner's.
- **The owner's copy of the brain,** `C:\AI-Brain-Link\<repo name>`, is synced by Obsidian's Git plugin where the owner has Obsidian. Where they don't, each job brings it up to date before its command runs (a fast-forward only, in `pc-run.yml`), so the setup scripts in it are current once any job has run. Nothing sends the owner's own edits in that copy without Obsidian: a job commits and pushes them when they ask.
- **PowerShell 5.1 quirks** (double quotes stripped on the way to programs, `"$p: text"`, stderr as errors, encodings, one-item lists, the runner's PATH): the [windows-powershell skill](../windows-powershell/SKILL.md). Read it before writing a job.
- **The script policy is `RemoteSigned`** for the owner's account (the installer set it); the runner's wrapper needs it. If it ever changes back, give the owner the command: `Set-ExecutionPolicy RemoteSigned -Scope CurrentUser -Force`. It says "Security error." when a narrower scope overrides it, though it saved the setting, so check with `Get-ExecutionPolicy -List` rather than trusting the error (an owner's PC, 22 Oct 2026).
- **A tool installed after the runner started isn't found by jobs** until the runner restarts: jobs get the PATH it started with, and on Windows the runner never reads its `.path` file (an owner's PC, 22 Oct 2026). Start the job with the PATH reload in the [windows-powershell skill](../windows-powershell/SKILL.md), or restart the runner. `start-runner.ps1`, beside the runner, starts it again a minute after it stops, with the PATH read fresh, so ending its `Runner.Listener` process restarts it. That inside a job kills the job, so the job leaves a one-off task that does it two minutes later; start the next job once three minutes have passed:
  ```
  $at = (Get-Date).AddMinutes(2).ToString('HH:mm')
  schtasks /create /tn "Restart the runner" /tr "taskkill /f /im Runner.Listener.exe" /sc once /st $at /f
  ```
  On a PC still on the older service, the task restarts the service as SYSTEM instead: `/tr "powershell -NoProfile -Command Restart-Service actions.runner.*" /ru SYSTEM`.
- **`winget` can't install a zip package from a job** (FFmpeg's `Gyan.FFmpeg`: "Failed to extract the contents of the archive"): it unzips through the Windows shell, which the older service didn't have; a runner started at sign-in may manage it, so try winget first. Installer packages, like Python and Node, are fine. For a zip, take its `Installer Url` and `Installer SHA256` from `winget show <id>`, download it with `curl.exe -L`, check `(Get-FileHash <zip>).Hash` against it, unzip it with `tar.exe -xf <zip> -C C:\AI-Brain-Link\Tools`, add its `bin` folder to the owner's PATH (`[Environment]::SetEnvironmentVariable('Path', [Environment]::GetEnvironmentVariable('Path', 'User') + ';<bin folder>', 'User')`; the older service needs the PC's, `'Machine'`, which needs admin rights), and restart the runner as above (an owner's PC, 22 Oct 2026).
- **Code lives in the repo, data lives on the PC.** Scripts stay in the repo (a skill's folder); a job checks the repo out and reads and writes its data under `C:\AI-Brain-Link\<Project>\<Stage>\<job>\`. Big data can go on another drive if the PC has one ([the PC's note](../../knowledge/systems/my-pc.md) lists them).
- **Workflows for the PC** use `runs-on: [self-hosted, my-pc]` (add `gpu` if it needs the GPU). Everything else keeps `ubuntu-latest`, so the index workflow stays on GitHub's machines.
- **Safety.** A runner job can do anything the owner can on their PC. PC workflows are started only by `workflow_dispatch` or a schedule, never by a pull request. The repo must stay private, and nobody else gets write access while the runner is attached. Never put a key in a `command`: commands show in the Actions list and the logs; add it as a secret and pass it in the workflow's `env` (the core's secrets gate). Deleting the owner's files needs their say first, and goes to the Recycle Bin where possible.

## Seeing what runs
The desktop shortcut "AI Brain Link - live jobs" opens [`watch-jobs.ps1`](watch-jobs.ps1) (installed in `C:\AI-Brain-Link\Tools\`). It follows the newest log, showing each command and its output live. Without the shortcut, the owner pastes `powershell -NoExit -ExecutionPolicy Bypass -File C:\AI-Brain-Link\Tools\watch-jobs.ps1` into PowerShell. The full history is the repo's Actions tab, under "Run on my PC".

## Setting it up again
[`setup-runner.ps1`](setup-runner.ps1) sets the runner up, or again from scratch: it puts Git on the PC's PATH and finishes Git's first-run setup, downloads GitHub's runner, registers it with this repo (it removes an old registration first), makes it start hidden when the owner signs in (a task in Task Scheduler, "AI Brain Link runner - AI-Brain-Link", or their startup list where Windows won't allow the task) and starts it now, starts it again if it ever stops, sets the script policy, adds the live jobs shortcut, and offers to keep the PC awake while plugged in. It says it's done only once GitHub sees the runner online. It needs no password and no admin rights; on a PC still on the older service, it asks for admin rights once, to take the service off. Give the owner this command to paste into PowerShell:
```
powershell -ExecutionPolicy Bypass -File "C:\AI-Brain-Link\<repo name>\skills\my-pc\setup-runner.ps1"
```
It needs GitHub's `gh` tool signed in, which the installer did. Its lines go to `C:\AI-Brain-Link\_logs\runner-starts.log` each time the runner starts or stops. `C:\AI-Brain-Link\<repo name>` is where the installer puts the brain's copy; a brain cloned somewhere else has its folder in [the PC's note](../../knowledge/systems/my-pc.md), so use that in this command and the ones below.

## If the runner stops picking up jobs
1. **Runs sit in "queued":** the PC is off or asleep, nobody is signed in, it's busy with another job, or the runner has stopped. `python3 skills/brain-spec/devices.py status` tells which in about a minute. If it's off, ask the owner to check the PC is on and they're signed in; signing out and in again starts the runner afresh. On a PC still on the older service, give them this to paste into PowerShell as administrator instead: `Get-Service actions.runner.* | Restart-Service`.
2. **The runner's own logs** are in `C:\AI-Brain-Link\_runner\_diag\`, and each start and stop is in `C:\AI-Brain-Link\_logs\runner-starts.log`.
3. **Still nothing:** have the owner run `setup-runner.ps1` again (above). On a PC still on the older service, a changed Windows password is the usual cause of a service that won't start; running the setup again moves it to starting at sign-in, which needs no password.
4. **After the runner ran under another account** (the older service included), delete the runner's checkout folder in `C:\AI-Brain-Link\_runner\_work\` once, or git refuses it ("dubious ownership").
5. **A runner set up by hand** from GitHub's "New self-hosted runner" page never picks up jobs: that page's `config.cmd` line has no `--labels my-pc`. Run `setup-runner.ps1`, which adds the labels (an owner's first brain, 21 Oct 2026).
6. **To see the PC's state while the runner is down,** give the owner the setup check with `-Send`. It changes nothing, and saves its report in this repo as `knowledge/systems/setup-check.md`, so you can pull and read it:
   ```
   powershell -ExecutionPolicy Bypass -File "C:\AI-Brain-Link\<repo name>\skills\my-pc\check-setup.ps1" -Send
   ```
   It checks the brain it's in, even when Obsidian lists an older vault first (an owner's PC, 31 Oct 2026, before it did).
7. **No runner at all, after the installer:** the setup stopped before its runner step. The installer keeps each step in `C:\AI-Brain-Link\_logs\install.log`, and the setup check's "The installer's last run" part says where it stopped. Give the owner the `setup-runner.ps1` command (above) to paste.
